## 클래스별 분석 및 목표
- Switch: SyncVar hook이 없고 ToggleSwitch가 권한 검사 없이 상태를 반전한다. 서버의 명시적 상태 설정과 멱등 갱신을 추가하고, hook은 표시만 갱신하도록 분리한다.
- LayerBasedSwitch: 클라이언트에서도 트리거가 상태를 바꾸고 진입/이탈마다 반전해 다중 접촉 시 상태가 틀어질 수 있다. 서버에서 유효 접촉 집합을 관리하고 최종 접촉 해제 시 비활성화한다. 일회 누름 동작은 별도 콜백으로 제공한다.
- OnOffManager (12): 그룹 상태가 비동기화 필드이고 소속 스위치의 내부 상태를 맞추지 않는다. 서버 그룹 상태를 기준으로 switch·지형·벨트를 적용하고 초기값은 OnStartServer/OnStartClient 및 hook에서 일관되게 반영한다.
- OnOffSwitch (60): 자신의 과거 bool을 반전해 매니저로 전달한다. 입력은 매니저의 현재 상태를 반전하도록 요청하고, 소속 상태 적용은 매니저를 재호출하지 않는 경로로 처리한다. 재귀·중복 토글을 막고 쿨다운 정책은 유지한다.
- Conveyor (27): Start가 방향을 true로 덮어쓰며 중첩 반복으로 애니메이터를 중복 갱신한다. 고정 방향/그룹 제어 소유권을 명시하고 시작 순서에 무관하게 최신 상태·색·애니메이션·게임플레이 방향을 한 번씩 적용한다.
- DoorSwitch (32): RPC에서 대상의 컴포넌트를 매번 찾고 상위 그룹 10개에는 자기 SpriteRenderer가 없다. 유효 스위치 상태로 문 표시/충돌을 적용하고 렌더러·콜라이더를 캐시한다. 여러 스위치가 같은 문을 참조하면 현재 AND/OR 의도를 먼저 확인한다.
- DetectPlatformResetBtn (5): 레이어 판정과 무관한 RPC 호출 및 중복 호출 경로가 있다. 유효한 서버 누름 1회에 서버 발판 리셋을 1회 실행하고 클라이언트는 결과만 반영한다.
- RespawnHandler (13): 플레이어 Teleport와 RPC의 일반 오브젝트 이동이 섞여 있다. 서버가 대상별 리셋 API를 호출하도록 통합하고 플레이어는 ServerMover.Teleport, 상자는 PickupObj의 서버 API를 사용한다. onlyBoxReset의 현재 의미를 단계 시작 시 확정한다.
- PickupObj (9): 자기 Reset 트리거, RespawnHandler, 소환 스위치가 각각 위치를 변경한다. 서버 리셋 API로 위치·속도·운반 상태·syncedPosition을 원자적으로 정리한다. 기존 Release와 추락 복귀도 같은 내부 경로를 사용한다.
- ObjSummonSwitch (9): 상자의 transform을 직접 이동시키고 버튼 표시도 서버에서만 갱신한다. 검증된 대상의 서버 리셋 API를 호출하고 쿨다운/버튼 상태를 동기화한다. 사용하지 않는 triggeringPlayer와 오해를 부르는 메서드 이름을 정리한다.
- PlatformController (직접 5): 경로 계산·승객 이동·RPC가 한 클래스에 섞이고 Controller2D.Move가 플레이어 예측 밖에서 실행된다. 우선 경로 평가·운행 상태·승객 처리를 분리한다. 속도의 기존 의미(구간 진행률/초)는 유지한다.
- PlayerDetectPlatform (88): 다수 bool, 복귀 코루틴, 렌더링 RPC가 얽혀 있고 ResetPlatformState가 경유점 진행률·대기 시간·원위치 복귀를 완전히 초기화하지 않는다. 대기/출발 지연/이동/완료/복귀 상태로 정리하고 서버 리셋에서 경로·타이머·코루틴·콜라이더·연출을 함께 초기화한다.
- MovingTrap (104): 이미 시작 시각 기반으로 이동한다. 계산 방식을 유지하며 경로·속도·시간 입력 검증과 정지/왕복/회전 회귀 검사에 집중한다. 불필요한 NetworkTransform은 추가하지 않는다.
- RotatingObstacle (37): 서버 회전과 NetworkTransform이 있으며 랜덤 선택은 Start에서 양쪽 실행 가능하다. 랜덤은 서버에서 확정한다. 시간 기반 회전 전환은 현재 결과와 성능을 비교한 뒤 별도 변경으로 진행한다.
- CannonShooter (69): 발사·투사체 이동 초기화·수명이 혼재하고 속도를 ClientRpc에 의존한다. 서버에서 투사체 초기 상태를 정한 뒤 스폰하고 클라이언트는 동기화 상태를 따른다. 발사 간격·방향·투사체 필수 컴포넌트 검증과 중지 시 예약 해제를 추가한다.
- SavePoint (14): 체크포인트 선택이 서버/클라이언트 접촉에 의존한다. 서버에서 진행 ID의 단조 증가를 보장하고 리셋·추락·운반 상태와의 경계를 확인한다. 위치와 ID는 그대로 보존한다.
- DynamicObj (6): 네트워크 매니저를 직접 캐스팅하고 현재 위치에 오프셋을 더한다. 서버의 인원 수를 안전하게 읽고 초기 위치 기준으로 1회 계산해 중복 적용을 막는다.
- BasicTrap/StagePartBehaviour: 넉백·네트워크 부품 기반 역할을 유지한다. 기본 스테이지는 루트 NetworkIdentity 하나, 팔레트 독립 프리팹은 기존 Variant 구조를 보존한다.
- RaycastController: 스위치·발판·상자의 공통 기반이다. 필요한 로컬 컴포넌트 검증과 유효 레이 개수/간격만 보강하고 플레이어 충돌 알고리즘을 일괄 교체하지 않는다.
- BuiltInMapCatalog/StageManager/FallBoundary/GameManager: 로딩·추락·클리어 흐름은 유지한다. 카탈로그·씬 참조·spawnPrefabs 등록·21개 생성/정리 회귀를 추가하고 로더의 광범위한 재분리는 후순위로 둔다.

- 에디터용 검사기를 기존 PlayingScripts/Editor 영역에 추가한다. 결과에는 스테이지·오브젝트 경로·클래스·필드·심각도·복구 후보를 기록한다.

## 단계 4 — 이동·감지 발판
- 범위: PlatformController, PlayerDetectPlatform. 단계 3의 리셋 버튼과 함께 최종 동작을 검증한다.
- 복구: spriteRenderer null 6개는 연출 옵션과 실제 로컬/자식 렌더러를 확인해 연결하거나 의도적인 미사용으로 명시한다.
- 복구: Stage 21 감지 발판 passengerMask를 복구한다. Stage 12 일반 발판 2개·20의 3개는 탑승형/장애물형을 확정한 뒤 마스크를 보존하거나 연결한다.
- 승객 운반은 플레이어 예측과 충돌하므로 별도 변경 단위로 구현한다. 기존 속도·위상·대기를 보존한 시간 기반 발판 이동량을 서버/소유 클라이언트의 Simulate에 같은 규칙으로 적용하는 방안을 우선 검증한다.
- 검증: 시작 지연·왕복·완주·낙하·복귀·이동 중 리셋, 코루틴 잔존 없음, 다중 승객·상자 지원 범위, 지연 조건에서 보정 떨림/관통 여부.
- 완료: 리셋 시 초기 위치와 모든 진행 상태가 복원되고 호스트/원격 클라이언트의 발판 위치·판정·승객 이동이 일치한다.

## 단계 5 — 장애물·발사체·인원별 배치·전체 회귀
- 범위: MovingTrap, RotatingObstacle, CannonShooter, DynamicObj와 로딩/공통 기반의 필요한 보강.
- 복구: 전체 대포의 projectilePrefab·Rigidbody2D·NetworkIdentity·클라이언트 spawn 등록, 회전 장애물의 동기화 대상, Stage 1~6 위치 동기화 참조를 검사한다.
- 검증: 발사 지연·주기·속도·파괴 범위, 서버 전용 발사체 이동, 서버 확정 랜덤 회전, 1~4인 시작 위치, 이동/회전 경로·콜라이더 변경 없음.
- 완료: 21개 스테이지 로드/클리어/정리 및 영향받은 맵 에디터 팔레트 테스트 플레이에서 기존 동작이 유지된다.

## 모든 단계의 검증·마이그레이션 완료 기준
- 프리팹 변경은 Unity 에디터의 SerializedObject/PrefabUtility로 수행하고 재로드한 저장 에셋을 다시 검사한다. YAML 대량 편집·GUID 수동 생성은 하지 않는다.
- 직렬화 필드명/타입은 우선 보존한다. 이름 변경은 FormerlySerializedAs, 타입/소유권 변경은 명시적 에디터 마이그레이션과 변경 전후 값 대조로 처리한다.
- 필수 참조 누락은 오브젝트 경로를 포함해 진단하고 해당 동작을 안전하게 중단한다. 정상 선택 값이나 의도적 고정 방향은 오류로 취급하지 않는다.
- 코드 변경마다 Assembly-CSharp 빌드와 Unity 컴파일/Mirror Weaver를 확인한다. 새 에디터 코드가 있으면 해당 에디터 어셈블리도 검사한다.
- 순수 상태 전이는 작은 독립 어셈블리의 EditMode 테스트로, MonoBehaviour/프리팹 통합은 에디터 검사·PlayMode/MCP 검증으로 확인한다. 기존 테스트 asmdef가 Assembly-CSharp를 직접 참조한다고 가정하지 않는다.
- 네트워크 검증은 호스트+원격 클라이언트 및 LocalNetworkTest 지연 조건을 포함한다. 게임 중 신규 입장 허용 정책은 바꾸지 않고 초기 스폰 시 SyncVar 적용을 검증한다.
- 실제 실행하지 못한 2~4인·Steam·서버 전용 검증은 통과로 표시하지 않는다. 각 단계의 미해결 설계 항목도 완료와 구분한다.
- 각 단계 결과는 해당 기능 문서의 현재 상태·검증·다음 작업에 반영하고 기존 미커밋 변경을 보존한다. 독립 문서가 필요하면 라우터에 등록한다.
